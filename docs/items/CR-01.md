# CR-01: snapshot table and row persistence

Status and dependencies live in the canonical backlog (`todo.md`, Phase 1 › Crawl).

- Target references: ARCHITECTURE.md §4 (Crawl & snapshot: "`snapshot` row links entity, URL,
  hash, time"), §5 `snapshot` table. Builds on AD-06/AD-08 (`FetchResult`) and CH-03
  (`core/chunk_store.py`, `chunk.snapshot_id`); follows the RT-01 SQLAlchemy pattern (`core/runs.py`).
- Objective: a `snapshot` table and `record_snapshot(engine, *, entity_id, url, result, source_kind)
  -> int` in `core/snapshot_store.py` that stores one fetch's metadata and its body's sha256, and
  returns the row id that `store_chunks` takes as `snapshot_id`.
- Columns (ARCHITECTURE §5): `id`, `entity_id` (integer, nullable, indexed; no FK until the entity
  table row lands), `url`, `final_url`, `content_type`, `sha256` (64 lowercase hex, indexed),
  `fetched_at` (timezone-aware UTC), `source_kind` (string). Snapshots are immutable: each call
  inserts a new row; no update or delete path.
- Non-goals: storing raw bytes (raw storage backend is an open (D) decision), the crawler, CLI
  `crawl`/`parse` wiring, the entity table, migrations, edits to `core/chunk_store.py`.
- Connections / scale: **unwired by design**; the Crawl row's CLI `crawl` stage calls it per fetch.
  One row per call, hashing `body_bytes` already in memory (the `FetchResult` byte cap bounds it).
