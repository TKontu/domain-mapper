# LM-02: bounded concurrent assess pairs in the live M1 driver

Status and dependencies live in the canonical backlog, not duplicated here.

- Origin: live118-m1 lane latency (verify ~610 s, extract ~242 s average per pair, pairs run
  serially). ARCHITECTURE §6 (local routing); LL-03/LL-04 driver rules (redaction, degraded exit)
  stay intact. No design change.
- Objective: `scripts/live_m1_run.py --jobs N` (int, default 1, valid 1..8, else argparse error
  exit 2) runs the per-pair `landscape assess` subprocesses through a bounded
  `concurrent.futures.ThreadPoolExecutor(max_workers=N)`; `--jobs 1` behaves exactly as today.
  `summary.json` gains `"jobs": N`; `steps` keeps the assess steps in pair order (not completion
  order). A fatal assess exit (not 0/1) stops submitting/cancels not-yet-started pairs, waits for
  running ones, and sets `failed_step` to the first failing pair's label in pair order; later
  stages are skipped as today.
- Acceptance: tests show (a) `--jobs 0` and `--jobs 9` exit 2; (b) with jobs=3 and a stubbed slow
  runner, peak concurrent assess calls is >1 and <=3, and steps are in pair order; (c) jobs=1 order
  and summary unchanged except the new `jobs` key; (d) a fatal exit in one pair yields
  `failed_step` = that pair's label, no post-assess stage runs, return 1; (e) redaction/scrub tests
  still pass. Full local gate green.
- Residuals: SQLite concurrent writers rely on the driver's busy timeout; not seen live; the
  gateway's own concurrency limit is unknown.
