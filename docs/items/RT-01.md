# RT-01: Run/work-unit tracking table + resumable stage runner

Status and dependencies live in the canonical backlog (`todo.md`, Phase 0 › Repo & infra).

- Target references: ARCHITECTURE.md §1 (idempotent, resumable stages; work-unit status
  `pending/done/failed/needs_review`; provenance `run_id`), §5 (`run` table), §11 (PostgreSQL 16);
  D-003.
- Objective: `core/runs.py` provides a `run` table and a `work_unit` table
  (`run_id, stage, unit_key, status, attempts, error, input_hash, updated_at`;
  unique `(stage, unit_key, input_hash)`) plus a `StageRunner` that, given a stage name, an
  iterable of `(unit_key, input_hash)` pairs and a handler, creates a run row, skips units already
  `done` for the same input hash, runs the rest, records `done`/`failed` per unit with the error,
  and marks the run `finished`/`failed`. Re-running after a crash resumes only non-`done` units.
- Scope: `core/runs.py`; the `DM_DATABASE_URL` setting in `core/config.py` and `.env.example`
  (default a local PostgreSQL URL matching compose.yaml's `DM_POSTGRES_*` placeholders); the
  `sqlalchemy` and `psycopg` runtime dependencies; `create_all` schema helper; `tests/test_runs.py`
  (offline, in-memory SQLite) and the setting's tests in `tests/test_config.py`; and, on planner
  review, the CLI dry run masking the URL password in `core/cli.py` (+ `tests/test_cli.py`).
- Non-goals: stage bodies and their CLI wiring (`core/cli.py` keeps its PF-04 behaviour; the only
  change is masking `database_url`), `llm_call` logging, scope tables, schema migrations (the
  migrations tool is a later item; `create_all` is the interim path), concurrent stage bodies.
- Acceptance: tests show (a) a fresh run executes all units and records `done`; (b) a handler
  failure records `failed` with the error and the run `failed` while other units are still
  processed; (c) a second run with the same inputs executes nothing, and a changed input hash
  re-executes only that unit; (d) failed units are retried on re-run with `attempts` incremented.
  The gate (unittest, pytest, ruff, mypy) passes offline.
- Scale / transaction bound: units are consumed lazily from the iterable and never materialised as
  a list; each unit commits a claim (attempts+1, pending) and then its outcome in two short
  transactions of its own (no batch; the handler runs outside both, since 97/A1), and run rows are opened and closed in one transaction each. A stage body therefore
  sees a durable `done`/`failed` after every unit, which is what makes a crash resumable. A
  handler's own effects are not part of that transaction, so stage bodies must be idempotent.
- Connections: `StageRunner` is **unwired by design**; its first production caller is the first
  stage body (Phase 1 Discover row) through the CLI. `core.runs.create_db_engine` is the intended
  construction point there, using `Settings.database_url`. The CLI dry run prints the URL with its
  password masked (and hides an unparsable value); `Settings.database_url` is excluded from
  `repr`. Every CLI engine (app/cli.py) is built through `create_db_engine` (assignment 95/A1).
  `landscape screen` (`run_screen`) is StageRunner's first production caller (assignment 97/A1):
  unit key = entity id, input hash = sha256(scope id + entity text), attached to the invocation's run
  row via `run_id=`; the budget stop records the unit `failed` and stops the run. Unit claim and
  outcome now commit in two short transactions with the handler between them. Other stages unwired.
- Evidence / residuals: PR #11 merged (head 7ac1c7d; planner review added URL-password masking, planner merged main for lockfile conflict), round 4. Seen on in-memory SQLite on main dc3ae93; **partial** until a Postgres run. Residuals: the PostgreSQL path is
  unexercised here (no docker on the host); the optional test runs only when
  `DM_TEST_DATABASE_URL` names a disposable database (it drops and recreates the two tables) and is
  otherwise reported as skipped. Schema creation uses `create_all` until the migrations item lands.
  There is no lease/lock against two runners processing the same unit concurrently; the unique
  constraint prevents duplicate rows but not duplicate handler calls. `needs_review` rows are
  treated as unfinished and re-run. Since 97/A1 the handler runs outside any runner transaction, so a slow
  handler holds none; a process crash mid-handler keeps the incremented attempt and leaves the unit
  `pending`, so a resume retries it.
