# LM-04: bounded concurrent screen LLM calls

Status and dependencies live in the canonical backlog, not duplicated here.

- Origin: live118-m1 lane latency and HANDOFF round 126 ("LLM concurrency in screen still
  unplanned"). ARCHITECTURE §6 (local routing); LB-01 run budget; AB-01/CR-16..18 run-close
  rules; StageRunner ledger semantics stay intact. No design change.
- Objective: `landscape screen --jobs N` (int, default 1, valid 1..8, else exit 2) overlaps up
  to N `screen_entity` calls on a bounded `concurrent.futures.ThreadPoolExecutor`, prefetching
  at most N units ahead of the StageRunner. `record_screen_result`, per-entity output lines and
  unit records stay on the main thread in entity id order. `--jobs 1` behaves exactly as today.
  `LlmBudgetExceeded` cancels not-yet-started calls; running calls finish and their results are
  discarded (those entities stay unscreened). `BudgetedLLM.spent` is summed under a lock.
  `scripts/live_m1_run.py` passes its `--jobs` value to screen.
- Acceptance: tests show (a) `--jobs 0`/`--jobs 9` exit 2; (b) jobs=3 with a slow fake: peak
  concurrent calls >1 and <=3, rows and output lines in id order, same counts as jobs=1;
  (c) jobs=1 output identical to the default; (d) budget exceeded with jobs=3: run stops, later
  entities unscreened, exit 1, run row failed; (e) concurrent wrapper calls sum `spent` exactly;
  (f) driver passes `--jobs` to screen. Full local gate green.
- Residuals: SQLite `llm_call` writes from worker threads rely on the busy timeout; with N>1,
  up to N calls may pass the budget check together, so overshoot can reach N calls; a unit the
  StageRunner skips as already done may still have been prefetched (one wasted call); not seen
  live.
