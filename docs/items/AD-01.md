# AD-01: `LLM` adapter — OpenAI-compatible (vLLM) + Anthropic, JSON-schema output

Status and dependencies live in the canonical backlog (`todo.md`, Phase 0 › Adapters).

- Target references: ARCHITECTURE.md §6 (one interface; OpenAI-compatible client for vLLM, Anthropic
  client for Claude; every call logged in `llm_call`), §4 pipeline stage 7 (structured output via
  JSON schema / vLLM guided decoding, untrusted evidence in the prompt), §5 (`llm_call` columns),
  §8 (LLM cost/latency observability); D-003; docs/items/RT-02.md (`core/llm_calls.py`);
  `core/config.py` (`llm_gateway_url`, `local_model`, `cloud_api_key`, `cloud_llm_model`).
- Objective: `adapters/llm.py` (the `adapters` package marker already existed from PF-01) defines an
  `LLM` protocol with `complete(prompt, *, purpose, run_id, json_schema=None) -> LlmResult` and two
  implementations. `LlmResult` carries `text`, `parsed` (a JSON object only when a schema is given),
  `tokens_in`, `tokens_out`, `cost` and `cache_hit`. `OpenAICompatibleLLM` posts to
  `{base}/chat/completions`; a schema is sent as `response_format: {type: json_schema, ...}` or, for
  vLLM guided decoding, as `guided_json`. `AnthropicLLM` posts to `/v1/messages` with a single forced
  tool whose `input_schema` is the caller's schema, and returns the tool's input as `parsed`. Every
  call runs inside `core.llm_calls.log_llm_call`, so exactly one `llm_call` row is written per call,
  success or failure. HTTP goes through an injectable transport callable; the default
  `urllib_transport` uses only the standard library. `build_llm(settings, backend)` maps
  `local`/`vllm`/`openai` to the gateway with `local_model`, and `cloud`/`anthropic`/`claude` to
  Anthropic with `cloud_llm_model`, refusing a cloud backend without a key. Both constructors accept
  optional per-million-token prices so `cost` is a figure with a stated basis; it defaults to `0.0`.
- Scope: `adapters/__init__.py` (already present), `adapters/llm.py`,
  `tests/test_llm_adapter.py`, `docs/items/AD-01.md`.
- Non-goals: `pyproject.toml`/`uv.lock` changes, real network calls in the gate, retries, per-run
  budget enforcement, prompt caching, CLI wiring (`core/cli.py` belongs to A1), edits to
  `core/llm_calls.py`, `core/config.py`, `todo.md` or `ARCHITECTURE.md`.
- Acceptance: fake transports and in-memory SQLite show (a) each backend sends the right URL,
  headers (API key only in its header) and schema field, and parses text and usage; (b) with a
  schema, parsed JSON is returned and invalid JSON raises `LlmSchemaError`; (c) exactly one
  `llm_call` row per call with `run_id`, tokens and `latency_ms >= 0`, and one `error` row on HTTP
  failure or schema failure whose text contains neither the prompt nor the response body; (d)
  `build_llm` selects the backend from `Settings` and refuses Anthropic without a key. Additional
  tests cover no-Authorization without a key, trailing-slash URL joining, cost arithmetic, timeout
  propagation, invalid timeout/schema-mode/max-tokens, and prompt/API-key absence from every row
  column and from the structured log.
- Scale / transaction bound: one HTTP request per call, no retry, no batch and no buffering beyond
  the single response body (bounded by the backend's configured output limit). Each call's
  row is committed by `log_llm_call` in its own short transaction when the adapter is given an
  `Engine`; a caller-supplied `Session` joins that caller's transaction, as RT-02 documents. The
  transport timeout is finite (`DEFAULT_TIMEOUT_SECONDS = 60`) and validated at construction.
- Connections: **unwired by design**. The first production callers are the Screen and Assess stage
  rows (Phase 1), which will construct the adapter with `build_llm`; `log_llm_call` gets its first
  production caller here. No CLI or schedule path reaches `adapters/llm.py` yet.
- Evidence / residuals: round 6, branch `task/ad-01-llm-adapter`, base 8206987; the PR body records
  the final head, packet digest and gate counts. Local gate offline on in-memory SQLite:
  `uv run python -m unittest discover -s tests` → 225 tests, OK (skipped=2); `uv run pytest` →
  223 passed, 2 skipped, 41 subtests passed; `uv run ruff check .` → passed;
  `uv run ruff format --check . --exclude ARCHITECTURE.md` → passed; `uv run mypy core adapters` →
  no issues in 9 source files. The adapter suite was run five times without flakiness.
  Residuals: no real gateway or Anthropic endpoint was contacted (offline gate), so wire-format
  compatibility with a live vLLM build and the live Anthropic API is unverified; the PostgreSQL path
  for `llm_call` is skipped here exactly as in RT-02 (only in-memory SQLite exercised). The adapter
  does not validate the returned object against the JSON schema itself: it trusts the provider's
  schema enforcement and only checks that the output parses to a JSON object. `cost` is `0.0`
  unless the caller supplies per-million-token prices (no price table is tracked here); `cache_hit`
  is always `False` because prompt caching is out of scope. HTTP error bodies are deliberately not
  read, so provider diagnostics are limited to the status code and its canned reason (the price of
  never leaking prompt/response text). OpenAI content must be a plain string (no multimodal
  blocks); Anthropic accepts a string tool input as raw JSON. There are no retries, rate-limit
  backoff or budget guard yet; those belong to later items. Prompt text and API keys are absent from
  rows, logs and exceptions; `prompt_hash` keeps RT-02's unsalted-SHA-256 caveat. The diff was
  checked for secrets and private-scope material (D-003): no scope, provider-specific or domain
  content, and no `.env` values are read or printed.
