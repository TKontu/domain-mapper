# RV-01: `landscape resolve` groups unresolved candidates by normalised domain

Status and dependencies live in the canonical backlog, not duplicated here.

- Target references: ARCHITECTURE.md §1 Resolve (normalise domains and names before matching candidates to entities) and §5 data model (`candidate(id, name, url, country_hint, segment_hint, source_id, query, found_at, resolved_entity_id)`); D-003 (no private scope words; examples and tests use `example.com`/`.invalid` hosts). Builds on DS-02 (`core/candidate_store.py`).
- Objective: `uv run landscape resolve --scope <dir>` reads unresolved `candidate` rows (`resolved_entity_id IS NULL`) and prints one `domain\tcount\tname` line per normalised domain (name = the earliest-inserted candidate's name), sorted by count descending then domain ascending, then `domains N candidates M`; a trailing `skipped K` line appears only when K > 0. Read-only: it writes no rows.
- Scope: new `core/resolve.py` (`normalize_domain`, `group_candidates`, `DomainGroup`, `ResolveSummary`), the `resolve` command in `core/cli.py`, `tests/test_resolve.py`, `tests/test_cli_resolve.py`. `normalize_domain`: http(s) only; host lowercased, IDNA-encoded to ASCII, trailing dot and leading `www.` stripped, port/path/query/fragment/userinfo dropped; IP literals kept as-is; anything else → `None`. Non-goals: entity table, merging, register lookup, public-suffix/registrable-domain logic, writes, migrations.
- Acceptance: offline tests cover the `normalize_domain` cases (`HTTPS://WWW.Example.COM:8443/a?b` → `example.com`; `http://example.com.` → `example.com`; IDN host → `xn--` form; `ftp://x`, `""`, `not a url`, `http://` → `None`; `http://[::1]/` → `::1`); resolved rows excluded (even on a domain with unresolved rows); rows whose URL normalises to `None` counted in `skipped K` only when K > 0; empty table → `domains 0 candidates 0`, exit 0; database failure → `error: database unavailable (<ExcType>)` on stderr, exit 2, no database URL; the command performs no INSERT/UPDATE/DELETE and leaves row count and contents unchanged.
- Connections / scale: production caller `landscape resolve` (`core.cli.run_resolve`); consumer is the future Resolve merge-suggestion row (unwired by design; that row also owns the entity table and register lookups). `group_candidates` streams with `yield_per(batch)` in `candidate.id` order, so memory is bounded by the number of distinct domains (plus one name per domain), not by the row count; `batch` defaults to 500 and a page boundary is tested at `batch` 1, 2 and 3.
- Base state: the base had no `resolve` command body — `resolve` appeared only in the `STAGES` tuple and was registered as the generic "not implemented yet" stage placeholder. This row replaces that one registration; the other stage placeholders are unchanged.
- Residuals: `a.example.com` and `example.com` stay separate (no public-suffix/registrable-domain logic); no name normalisation, entity table or merge suggestions; no migrations (`create_all`); PostgreSQL and a live database unexercised; IDNA uses Python's built-in IDNA 2003 codec; the README/PF-04 wording that every stage accepts `--layer/--limit/--dry-run` and exits 1 "not implemented yet" is now stale for `resolve` (fixing it is outside this assignment's file set).
- Outcome (round 31): merged PR #78 at head 213940e; seen on main 302c17c over the 5 live DS-02 rows (5 domains, exit 0). Review nits kept as residuals: `http://example.com:abc/` is accepted (port dropped unchecked); `http://www./` → `www`; `www.1.2.3.4` → `1.2.3.4`.
