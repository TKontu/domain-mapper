# RV-02: `landscape resolve --apply` creates and links `entity` rows per normalised domain

Status and dependencies live in the canonical backlog, not duplicated here.

- Item: todo.md Phase 1 "Resolve" row; builds on RV-01 (`core/resolve.py`, PR #78) and DS-02 (`core/candidate_store.py`).
- Architecture sections / approved decisions: ARCHITECTURE.md §4 stage 2 Resolve; §5 data model `entity(id, scope_id, group_id, name, primary_domain, status, created_run)` and `candidate.resolved_entity_id`; D-003 (tests use `example.com`/`.invalid` hosts only, no private scope words).
- Objective: `uv run landscape resolve --scope <dir> --apply` creates one `entity` row per normalised domain group of unresolved candidates (or reuses an existing entity with the same `scope_id` + `primary_domain`) and sets `resolved_entity_id` on those candidates; then prints `created C linked L skipped K` (skipped = unnormalisable URLs, left unresolved). Without `--apply` the command is unchanged (RV-01 read-only output).
- In scope: new `Entity` ORM model (`__tablename__ = "entity"`, §5 columns: `id`, `scope_id` String(255) = scope pack id, `group_id` int nullable no FK, `name` Text = group's first-found name, `primary_domain` String(255), `status` String(32) = "unscreened", `created_run` int nullable), unique constraint (`scope_id`, `primary_domain`); `core/resolve.py` gains `apply_resolution(engine, scope_id, *, batch=DEFAULT_BATCH) -> ApplySummary`; `--apply` flag in `core/cli.py` `resolve`; tests `tests/test_resolve_apply.py` (+ CLI cases). Rerun is idempotent: a second `--apply` prints `created 0 linked 0 skipped K`. Non-goals: name-based or register matching, merge suggestions, group/GLEIF, migrations (`create_all` as existing tables do), a candidate FK constraint, README stage-wording fix.
- Premises: (1) no `entity` table exists yet: `grep -rn '__tablename__ = "entity"' core` is empty; (2) `resolved_entity_id` is an indexed int with no FK: `core/candidate_store.py` Candidate; (3) `resolve` already has its own CLI body: `grep -n run_resolve core/cli.py`.
- Expected files: `core/entity_store.py` (new, model) or inside `core/resolve.py`; `core/resolve.py`; `core/cli.py` (resolve command only); new tests. Shared seam: `core.runs.Base` metadata (add the model so `create_all` sees it, as other stores do).
- Resources / artifacts: none; offline SQLite only. No network, no live DB, no paid APIs.
- Acceptance: offline tests show — 3 unresolved candidates over 2 domains → 2 entities, all 3 linked, names = first-found, status "unscreened", scope_id = scope id; rerun → `created 0 linked 0`; a new candidate on an existing entity's domain links to that entity (created 0 linked 1); already-resolved rows untouched; unnormalisable URLs counted in skipped and left NULL; same domain in two scope ids → two entities; one transaction per batch, a failure mid-run rolls back that batch only and the command exits 2 with `error: database unavailable (<ExcType>)` on stderr and no URL; without `--apply` output is byte-identical to RV-01 behaviour (existing tests pass unchanged).
- Connections / scale: production caller `landscape resolve --apply` (`core.cli.run_resolve`); `Entity` consumers: Screen/Crawl rows (unwired by design). Stream candidates with `yield_per(batch)` (default 500) in id order; keep only a domain→entity_id map in memory (bounded by distinct domains); UPDATEs batched per `batch` rows, committed per batch; test page boundaries at batch 1 and 2.
- Publication authority and PR evidence: open a PR to main from the assigned branch; do not merge. PR body: assignment identity/digest, head SHA, gate output with counts and skips, residuals (no migrations, Postgres unexercised, domain-only matching).

- Outcome (round 32): merged PR #80 at head 6069449 (merge e8be9ff); main gate 849 passed, 5 Postgres skips. Seen: `landscape resolve --scope scopes/_example --apply` on main e8be9ff over a copy of the 5 live DS-02 rows (`.agent-runs/32/live/rv02.sqlite`) → `created 5 linked 5 skipped 0`, rerun `created 0 linked 0 skipped 0`, then plain `resolve` → `domains 0 candidates 0`, exit 0. Implementation pages by keyset (one transaction per page) instead of one `yield_per` stream; memory still bounded. Residuals: no migrations, Postgres unexercised, domain-only matching, no candidate FK, concurrent `--apply` untested; entity `status` value `unscreened` chosen by the planner (§5 names no values).
