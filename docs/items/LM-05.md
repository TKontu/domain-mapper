# LM-05: local max-tokens cap in the live M1 driver

Status and dependencies live in the canonical backlog, not duplicated here.

- Origin: live118-m1 record (docs/runs/LL-01-M1.md): tokens out 38110 vs in 14317, 3 pairs hit the
  900 s per-call timeout, 5 of 6 failures on the first criterion. The driver can cap the verifier
  (LM-03) but not the extractor/screen output. ARCHITECTURE §6 (local routing); LL-03/LL-04 driver
  rules (redaction, scrubbing, degraded exit) stay intact. No design change.
- Objective: `scripts/live_m1_run.py --max-tokens N` (optional int, valid 1..8192, else argparse
  error exit 2) sets `DM_LOCAL_MAX_TOKENS=N` in the child environment, overriding any env-file
  value; omitted, the child env is exactly as today. `summary.json` gains `"max_tokens": N` or
  `null`. `DM_LOCAL_MAX_TOKENS` already caps screen and the assess extractor (app/cli.py
  `settings.local_max_tokens`) and the verifier when `DM_VERIFIER_MAX_TOKENS` is unset.
- Acceptance: tests show (a) `--max-tokens 0` and `8193` exit 2; (b) with 512 the stubbed runner's
  env has `DM_LOCAL_MAX_TOKENS="512"` even if the env-file sets another value, and the summary has
  512; (c) omitted: no override, summary null; (d) `--max-tokens` and `--verifier-max-tokens`
  together set both keys independently; (e) existing tests pass. Full local gate green.
- Residuals: not seen live; the cap's effect on extractor latency, timeouts and status quality is
  measured by the next live M1 lane.
