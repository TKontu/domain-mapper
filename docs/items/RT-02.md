# RT-02: Logging + `llm_call` cost/latency logging

Status and dependencies live in the canonical backlog (`todo.md`, Phase 0 › Repo & infra).

- Target references: ARCHITECTURE.md §5 (`llm_call(id, run_id, model, purpose, prompt_hash,
  tokens_in, tokens_out, cost, latency_ms, cache_hit)`; append-only history), §6 (every call logged
  in `llm_call`; per-run budgets are not enforced here), §8 (LLM cost/latency observability),
  §11 (PostgreSQL 16); D-003; RT-01 (`core/runs.py` `Base`/`Run`).
- Objective: `core/log.py` provides `configure_logging(level)` — one root `StreamHandler` with a
  structured formatter that renders each stdlib record as one line of `key=value` fields (newlines
  and tracebacks escaped). `core/llm_calls.py` provides an `LlmCall` model on the same declarative
  `Base` as `core/runs.py`, with the §5 columns plus `created_at`, `status` and `error` and a foreign
  key `run_id` → `run.id`; `record_llm_call(session_or_engine, ...)` writes exactly one row per call
  (prompt hashed, never stored or logged); `log_llm_call(...)` is a context helper that measures
  latency in milliseconds, writes the row on success **and** on failure (`status='error'`, capped
  error text) and re-raises the body's exception. One row per call in its own short transaction; no
  in-memory accumulation.
- Scope: `core/log.py`, `core/llm_calls.py`, `tests/test_log.py`, `tests/test_llm_calls.py`,
  `docs/items/RT-02.md`. `core/runs.py` is unchanged: `LlmCall` reuses its `Base`.
- Non-goals: the `LLM` adapter/client (Phase 0 › Adapters row), budget enforcement (a later item),
  CLI wiring (`core/cli.py` is untouched; owned by A1 in this round), schema migrations
  (`create_all` remains the interim path from RT-01), prompt/response persistence, edits to
  `todo.md` or `ARCHITECTURE.md`.
- Acceptance: tests show (a) a recorded call yields exactly one `llm_call` row with `run_id`,
  tokens, cost, `latency_ms >= 0`, `cache_hit` and `created_at`, with `prompt_hash` equal to the
  prompt's SHA-256 and the prompt text absent from every column and from the structured log;
  (b) the context helper records measured latency and usage and writes an `error` row when the body
  raises, re-raising the same exception; (c) one row per call, no buffering; (d) `configure_logging`
  emits exactly one line per record, including multiline messages and tracebacks, and reconfiguring
  replaces rather than duplicates its handler. The gate (unittest, pytest, ruff, ruff format, mypy)
  passes offline.
- Scale / transaction bound: every call commits its own row in one short transaction (an `Engine`
  gets its own session/transaction; a `Session` passed by a caller joins its open transaction by
  design), so cost/latency rows survive later failures and nothing accumulates in memory. The
  table grows one row per model call; it is append-only and carries indexes on `run_id` and
  (`run_id`, `created_at`) for per-run cost queries. `prompt_hash` is indexed for cache-hit analysis.
- Connections: **unwired by design**. The production caller is the `LLM` adapter row (Phase 0 ›
  Adapters), which will call `log_llm_call`/`record_llm_call` with the run it serves. There is no
  CLI path and no public symbol change outside `core/`; `configure_logging` is meant to be called
  once at process start by the CLI or adapter host, which has no caller yet (residual).
- Evidence / residuals: round 5, PR #14 merged (head 2b8a240); seen on in-memory SQLite (pytest on main 0789345); partial until a Postgres run. Executor PR body
  records the packet digest, final head SHA and gate counts); local gate run offline on in-memory
  SQLite at that head.
  Residuals: the PostgreSQL path is unexercised here (no docker/model endpoint; same residual as
  RT-01); schema creation still uses `create_all` until the migrations item lands. `cost` is stored
  as `NUMERIC(12, 6)` USD and is only as accurate as the adapter's own figure. `prompt_hash` is an
  unsalted SHA-256: it enables cache-hit and duplicate-prompt analysis but is not a secret and a very
  short prompt could be guessed from it. Error rows store the exception type/message (capped at 2000
  characters); the LLM adapter must not put prompt or response text into the exception, and the log
  record deliberately carries only the hash and counters, not the error message. When a caller
  passes an open `Session`, the row commits with that caller's transaction rather than independently.
  Per-run budget enforcement and cost aggregation are out of scope (later items).
